## 大阪VPS路由，到底在看什么？

先说个很多人搞混的概念。日本VPS的"线路"，说的不是你家宽带那种光纤入户，而是数据包从国内出发、经过哪些骨干网、在哪个节点跳转到日本上游运营商、最后怎么回国。这条路走得好不好，直接决定了延迟和速度。

大阪机房常见的上游线路有这么几条：

- **IIJ（Internet Initiative Japan）**：日本本土顶级运营商，AS2497。大阪、东京都有骨干节点，国内三网可以通过东京节点对接IIJ，再转到大阪。稳定性不错，延迟通常在70-90ms之间。
- **软银**：日本三大移动运营商之一，AS17676。对国内三网优化做得比较早，往返直连延迟很低，是大阪机房很受欢迎的线路。
- **NTT**：日本电报电话公司，全球 Tier 1 运营商。线路质量没问题，但国内对接路径有时候会绕，看具体机房配置。
- **CN2 GIA / 9929 / CMIN2**：这些是**国内出口**的优化线路，分别对应电信、联通、移动的优质骨干。日本机房如果接了这些，国内访问体验会明显好于普通163线路。

ZgoCloud 大阪机房走的是 **IIJ 线路**，机房位于 Equinix Osaka，租用的是 xTom 的网络（AS4785），再上联到 IIJ。下面我就把三网路由一段段拆给你看。

## ZgoCloud 大阪机房路由实测：三网去程回程全拆解

> 以下路由数据基于大阪 EPYC 系列和 Ryzen9 系列的实测，两个系列网络配置完全一致，区别只在 CPU 型号。

**电信路由：去程走163骨干，回程走IIJ直连**

电信用户的数据包出门后，先走电信163骨干网，直连到日本东京节点，然后转 IIJ 线路到达大阪机房。回程反过来，从大阪出发走 IIJ 到东京，再对接电信163骨干回国。

实测深圳电信回程路由片段大概是这样的：大阪 → xTom → BB Tower → IIJ 大阪节点 → IIJ 东京节点 → 电信东京节点 → 广州 → 深圳，最终延迟在72ms左右。

这个表现对于一个非CN2的日本机房来说算相当不错了。72ms意味着什么？大概就是你眨一下眼睛的时间，数据已经跑了个来回。

**联通路由：去程走AS4837，回程走IIJ对接AS4837**

联通的去程走的是 AS4837 骨干网（这是联通的优质线路，比普通169骨干强不少），同样直连东京后转 IIJ 到大阪。回程从大阪走 IIJ 到东京，对接联通 AS4837 回国。

实测北京联通回程，最终延迟在100ms出头。比电信稍高一些，但路径还算干净，没有大规模绕路。晚高峰时段的表现也比较稳定，没有出现明显的丢包。

**移动路由：去程略有绕道，回程走IIJ对接CMI直连**

移动是三网里最有意思的一个。去程方面，移动 CMI 会先到洛杉矶节点，然后转 Telstra 线路再到大阪——等于先往东跑了一趟美国再折回来，所以去程延迟会偏高一点。不过回程就舒服多了，直接从大阪走 IIJ 到东京，对接移动 CMI 直连回国，上海移动实测延迟在67ms左右。

换句话说，移动用户如果你主要是下载、看视频这类回程流量大的场景，体验其实很好；但如果你做的是需要频繁握手的小包业务，去程绕路可能会有感知。

**三网延迟汇总**：

| 运营商 | 平均延迟 | 去程路径 | 回程路径 |
|--------|----------|----------|----------|
| 电信 | ~72ms | 163骨干 → 东京 → IIJ → 大阪 | IIJ → 东京 → 163骨干直连 |
| 联通 | ~100ms | AS4837 → 东京 → IIJ → 大阪 | IIJ → 东京 → AS4837直连 |
| 移动 | ~67ms | CMI → 洛杉矶 → Telstra → 大阪（略绕） | IIJ → 东京 → CMI直连 |

整体来看，这套路由的核心逻辑是"回程统一走IIJ直连，去程各找各妈"。对于大多数以回程为主的使用场景（下载、看视频、网页访问），三网体验都算得上干净利落。如果你对移动去程延迟特别敏感，那可能需要考虑软银线路的机房；但如果你是普通用户，这点绕道基本无感。
